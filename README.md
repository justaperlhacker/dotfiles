# dotfiles

Personal configuration files managed with [GNU Stow](https://www.gnu.org/software/stow/).

## Install

Clone to `~/.dotfiles`:

```bash
git clone git@github-justaperlhacker:justaperlhacker/dotfiles.git ~/.dotfiles
```

## Install script

`install.pl` is a wrapper around Stow that **backs up any existing file or
directory before it is replaced**, so nothing is ever silently clobbered.

```bash
./install.pl --all                                     # stow every package
./install.pl --package bash --package nvim --package i3  # specific packages
./install.pl --list                                    # list available packages
./install.pl --help                                    # show options
```

`--all` and `--package` cannot be combined. Exit codes: `0` success, `2`
usage error, `1` failure (e.g. Stow conflict).

## Manual Stow usage

Stow creates symlinks from your home directory into the appropriate package directory.

```bash
stow bash             # install one package
stow bash nvim i3     # install several
stow -D bash          # remove symlinks
```

### Default terminal (`xdg-terminal-exec`)

Apps whose `.desktop` file sets `Terminal=true` (e.g. Cachy-Update) are launched
by GLib/DMS via `xdg-terminal-exec` on `PATH`. Without it, GLib falls back to a
hardcoded list in which `gnome-terminal` wins over kitty/konsole.

- `scripts` provides `~/.local/bin/xdg-terminal-exec`, a small wrapper that runs
  the first available terminal: kitty → konsole → terminator → gnome-terminal →
  alacritty → foot → ghostty → wezterm → xterm.
- `kitty` provides `~/.config/xdg-terminals.list` (`kitty.desktop`), the
  xdg-terminals spec list.

To use the packaged reference implementation instead, install `xdg-terminal-exec`
from `extra` and remove `~/.local/bin/xdg-terminal-exec` — it shadows the package
because `~/.local/bin` comes first on `PATH`.

### OpenCode session picker (`ocs`)

OpenCode scopes its session list to the directory you launch it from, so sessions
from other projects are invisible to `/sessions` and `opencode session list`.
`ocs` (in `scripts`) reads the local OpenCode database directly and shows every
top-level session in an fzf picker, grouped by project folder with the most
recently used first.

```bash
ocs                     # fzf picker; Enter resumes in the session's directory
ocs rust                # picker pre-filled with "rust"
ocs -l                  # plain list (no picker)
ocs --ids               # session IDs only
ocs --json              # full session data as JSON
ocs --show ses_abc123   # details for one session, incl. its last prompt
ocs -a                  # include archived sessions
ocs -d ~/Projects       # only that directory and below
ocs -n 20               # show at most N sessions
ocs --dry-run           # print the resume command instead of running it
```

The selection resumes with `opencode -s <id>` after changing into the session's
recorded directory — resuming from the wrong directory can 404 or create a
shadow session with the same ID. Ctrl-/ toggles the preview pane; without `fzf`
the script falls back to a numbered prompt. It honours `OPENCODE_DB`, `--db`,
and `NO_COLOR`, and refuses to resume a session whose directory no longer
exists.

### kitty cursor animations (`cursor_trail`)

Cursor animations are the builtin `cursor_trail` feature (kitty 0.37+, custom
shader styles from 0.49). They are **enabled** in `kitty.conf` — `cursor_trail`
set to a value larger than zero turns them on, `0` turns them off:

```conf
# Cursor trail
cursor_trail 2                    # enable; <ms> a cursor must hold still before
                                  # its movement gets a trail (lower = chattier)
cursor_trail_decay 0.2 0.6        # fade-out time range in seconds
                                  # (fastest slowest); lower = snappier fade
cursor_trail_start_threshold 1    # cells moved before the trail starts,
                                  # per axis; default 2 skips tiny steps
# cursor_trail_color #ff9e64      # trail color; default = cursor's color
```

Differences from the stock defaults (`0`, `0.1 0.4`, `2`): trails trigger on
smaller moves and fade a bit slower, tuned for trying to track big cursor
jumps around large code buffers. To tune live, press `CTRL+SHIFT+F5`
(`load_config_file`) to reload `kitty.conf` in the current window; no restart
needed. (`kitty @ load-config` also works, but needs `allow_remote_control`
enabled, which this config leaves off.)

Custom trail styles are set via `custom_shaders` in `kitty.conf`:

| Value                        | Effect                                  |
|------------------------------|-----------------------------------------|
| (none)                       | plain trail (current setup)             |
| `cursor-trail-motion-blur`   | smooths fast moves with motion blur     |
| `cursor-trail-blaze`         | fiery blaze style                       |
| `cursor-trail-railgun`       | particle stream flying off the cursor   |
| `cursor-trail-torpedo`       | torpedo-like particle burst             |
| `cursor-trail-pixiedust`     | fairy-dust particles                    |

The trail follows the text cursor only, and never appears while the cursor is
resting; only movement you can see gets animated.

### niri tray icons (XEmbed → SNI bridge)

DankMaterialShell's tray only speaks StatusNotifierItem, but Wine (EA App via
Lutris) and other legacy X11 apps use the XEmbed protocol. `xembedsniproxy`
bridges the two; without it Wine draws its own floating "tray" window.

niri tears Xwayland down when the last X11 app exits, which kills the proxy
too, so the `niri` package ships it as a systemd user service that is
restarted automatically instead of a one-shot `spawn-at-startup`.

The unit is scoped with `ConditionEnvironment=XDG_SESSION_DESKTOP=niri`, so
Plasma uses its own `plasma-xembedsniproxy.service` instead of starting a
duplicate.

```bash
sudo pacman -S --needed plasma-workspace   # provides /usr/bin/xembedsniproxy
systemctl --user enable --now xembedsniproxy.service
```

The `OneDriveGUI.desktop` autostart entry starts via
`~/.config/niri/scripts/exec-after-sni` because OneDriveGUI checks
`QSystemTrayIcon.isSystemTrayAvailable()` once at startup and silently skips
creating its icon if DMS's SNI host isn't registered yet.

### Brave appearance (niri)

In Brave's **Appearance** settings choose **Theme → GTK**, not the internal
**Dark** theme. Brave's Dark theme mixes Chromium's own menu colours with the
GTK menu background, which produces white-on-white hamburger menus with the
Breeze theme. GTK mode delegates the UI to the system theme, which
`dms-theme-sync` keeps in step with DMS.

The service switches `gtk-theme` between `Breeze` and `Breeze-Dark` (not just
the `gtk-application-prefer-dark-theme` flag) because running Chromium/Brave
windows only react to `notify::gtk-theme-name`. The flag is kept `false`
because it is read only at startup, so the explicit theme name is the live
channel. Brave therefore follows the sunset schedule without a restart. The
Brave file chooser is routed through the GTK portal for the same reason (see
`niri-portals.conf`).

After first setting this up (or after switching the GTK theme in a running
session), restart Brave once so it starts with the flag cleared; later
light/dark transitions are live.

### Per-machine overrides

Create `~/.config/bash/local` for machine-specific settings (gitignored).

### Per-host autostart (i3 and niri)

Host-specific startup is kept out of the shared configs so one machine can be
minimal without disabling programs for every host:

- **i3**: `autostart.conf` calls `scripts/autostart-host.sh`, which sources
  `~/.config/i3/scripts/autostart/<hostname>.sh`. Discord and Yakuake live in
  `destro.sh`; `blackslate.sh` is intentionally empty.
- **niri**: `niri-autostart.sh` sources
  `~/.config/niri/scripts/autostart/<hostname>.sh` (Discord is in `destro.sh`).
  Yakuake is started by its XDG autostart entry, so that systemd unit is gated
  to destro with
  `~/.config/systemd/user/app-org.kde.yakuake@autostart.service.d/10-host.conf`
  (`ConditionHost=destro`).

Add new per-host programs to the matching fragment. Keep the shared config for
things every machine needs.

### DMS light/dark sync (niri + GTK + KDE + Ghostty)

The `niri` package ships `dms-theme-sync.service`. It is enabled through
`niri.service.wants` (a local `systemctl --user enable` symlink, not stowed),
and keeps the rest of the session in step with DMS's location/sunset mode:

- writes `org.gnome.desktop.interface color-scheme` as `prefer-dark` or
  `prefer-light`. DMS writes `default` when going back to light, which makes
  the XDG portal report "no preference" and Electron apps (Discord) stop
  following the system.
- updates `gtk-application-prefer-dark-theme` in
  `~/.config/gtk-{3,4}.0/settings.ini` and keeps `gtk.css` importing only
  DMS's `dank-colors.css`. GTK3 has no `color-scheme` support, and Plasma's
  `colors.css` otherwise pins the Breeze palette to the last Plasma session.
- applies DMS's generated KDE scheme (`DankMatugenDark` / `DankMatugenLight`)
  with `plasma-apply-colorscheme`, so Dolphin and other KDE/Qt apps follow.
  The tracked `kde/.config/kdeglobals` is only a base template (stow-ignored);
  the service owns the real `~/.config/kdeglobals`. It also restarts
  `plasma-xdg-desktop-portal-kde.service` after a scheme change so the KDE
  portal's dialogs repaint.
- sends `SIGUSR2` to running Ghostty instances when DMS regenerates
  `~/.config/ghostty/themes/dankcolors` (Ghostty does not watch theme files).

After stowing on a new machine:

```bash
systemctl --user daemon-reload
systemctl --user enable dms-theme-sync.service
```

DMS must also have `terminalsAlwaysDark=false` for the generated terminal
palettes (Ghostty, kitty, …) to follow light mode.

The live `~/.config/kdeglobals` is generated the same way: the tracked
`kde/.config/kdeglobals` is only a base template (stow-ignored), and the
service seeds the real file from it on first use before applying a scheme.
The live file is authoritative for non-color keys (fonts/Xft, icon theme,
look-and-feel, file-dialog options); the service only rewrites color
sections and never overwrites an existing file. If you change non-color KDE
settings in Plasma and want them captured in the repo, refresh the base
explicitly:

```bash
cp ~/.config/kdeglobals ~/.dotfiles/kde/.config/kdeglobals
git add kde/.config/kdeglobals && git commit -m "kde: refresh kdeglobals base"
```

The DMS-generated theme outputs (`ghostty/.../dankcolors`,
`kitty/.../dank-*.conf`, `wezterm` colors, `zed` theme, `zen.css`, and
`niri/.config/niri/dms/colors.kdl`) are gitignored and stow-ignored. On
machines installed before `install.pl` switched to `stow --no-folding`, `~/.config/{ghostty,kitty,wezterm,zed}` may
still be folded symlinks into the repo, so DMS writes those files inside the
repo tree (ignored by git). To have DMS write to real home config dirs
instead, remove the folded symlink and re-stow the package:

```bash
rm ~/.config/ghostty        # removes only the directory symlink
./install.pl --package ghostty
```

Repeat for `kitty`, `wezterm`, and `zed` as needed.

### i3 automatic light/dark mode

i3 is X11 and does not run DMS, so `i3-theme-sync` reads the same KDE
NightTime D-Bus schedule that Plasma's Night Light and automatic
look-and-feel use:

```sh
gdbus call --session \
  --dest org.kde.NightTime \
  --object-path /org/kde/NightTime/Manager \
  --method org.kde.NightTime.Manager.Subscribe '{}'
```

The service is D-Bus-activatable, so it works from an i3 session once a
location has been stored (KDE keeps the location in
`~/.local/state/knighttimestaterc`). i3 has no desktop-shell GeoClue agent,
so the script starts `/usr/lib/geoclue-2.0/demos/agent`, waits for GeoClue,
and restarts `knighttimed`; this makes KDE use its cached location and real
sunrise/sunset instead of the 06:00/18:00 timed fallback. If GeoClue still
cannot start, the script falls back to the `[Times]` values in
`~/.config/knighttimerc` (06:00/18:00 by default).

`i3/.config/i3/scripts/i3-theme-sync` is started from i3's autostart with
`exec_always` (a lock keeps reloads from starting a second copy) and polls
every 60 seconds. On a mode change it:

- switches the i3 theme symlink to `github-dark` (dark) or `github-light`
  (light) via `switch-theme`, which also updates rofi and dunst and reloads
  i3. i3bar colors come from `set` variables in the active theme's
  `i3.conf`, with dark fallbacks in `appearance.conf`. The automatic pair is
  configured in `i3/.config/i3/theme-sync.conf`; see
  `i3/.config/i3/README.md` for the full theme documentation.
- sets GTK to `Breeze-Dark` / `Breeze` plus the matching icon theme, and
  temporarily removes the DMS `dank-colors.css` import from `gtk.css` so
  the real Breeze GTK theme is used. `dms-theme-sync` recognizes the
  `i3-theme-sync` marker and restores the DMS palette in niri.
- applies KDE's `BreezeDark` / `BreezeLight` color scheme, updates the
  look-and-feel/icon keys, and restarts both XDG desktop portals.
- switches kitty and Ghostty palettes through the shared
  `theme-session.d/active.conf` and `theme-session.conf` overrides. niri's
  `dms-theme-sync` writes the DMS palette back into those files, so the two
  sessions do not fight over the tracked terminal configs.

The `themes/active` symlink, `rofi/theme-active.rasi` and
`dunst/dunstrc.active` are generated and gitignored, so automatic switching
does not dirty the repo. For testing:

```sh
i3-theme-sync --get-mode            # current dark/light decision
i3-theme-sync --once                # apply the current mode and exit
i3-theme-sync --mode dark           # force the configured dark theme
i3-theme-sync --mode light
i3-theme-sync --theme github-dark   # apply one theme manually
i3-theme-picker                     # fzf picker for all i3 theme areas
```

The picker applies the selected theme to i3, i3bar, rofi, dunst, kitty and
Ghostty. It also applies Breeze Dark/Light when the theme has a `mode` file.
Manual picks are temporary; the scheduled pair resumes at the next
sunrise/sunset transition.

### Brave flags

`/usr/bin/brave` only ever reads `~/.config/brave-flags.conf`, so a
`.local/bin/brave` shim shadows it and layers the files in
`~/.config/brave-flags.d/`:

1. `default.conf` — session/host-agnostic defaults (always applied).
2. `<hostname>.conf` — used when present, otherwise:
3. `default-<session>.conf` — `default-wayland.conf` or `default-x11.conf`.

`~/.config/brave-flags.conf` keeps the common flags that `/usr/bin/brave`
applies itself (e.g. `--password-store`). Chromium honours only one
`--enable-features` value, so keep it to a single comma-separated line per file.

On `destro`, `brave-flags.d/destro.conf` pins the GL ANGLE backend (Vulkan
ANGLE crashes the GPU process on this machine) and enables VA-API
decode/encode on the RX 6700 XT, while keeping the headless RTX 3060 out of the
VA-API path.

### Keyboard remap (Caps Lock → Ctrl, Right Alt → Super)

All three sessions use the same remap:

- **Caps Lock** acts as an additional Left Ctrl, with no Caps Lock toggling
  (`caps:ctrl_modifier`, a stock xkeyboard-config option).
- **Right Alt** acts as an additional Left Super (`Super_L`), via the local
  option `custom:ralt_super`. This keyboard has no Right Win key, so no
  swap option is involved.
- Every other key is unchanged.

The shared pieces live under `kde/.config/`:

- `kxkbrc` sets `Options=caps:ctrl_modifier,custom:ralt_super` and
  `ResetOldOptions=true` (KWin ignores `Options` without it).
- `xkb/symbols/custom` defines `ralt_super`, which maps `<RALT>` to `Super_L`.
- `xkb/rules/evdev` is a per-user overlay of the system rules, including
  `evdev-system` (a symlink to `/usr/share/X11/xkb/rules/evdev`).

niri uses the same options in `config.kdl`. i3 cannot use
`setxkbmap -option custom:ralt_super` because X11's `setxkbmap` does not
search `~/.config/xkb/rules` and does not forward `-I` to `xkbcomp`. Its
autostart runs `i3/.config/i3/scripts/set-keymap`, which generates the keymap
with `setxkbmap -print` and loads it with the local include path:

```sh
setxkbmap -model pc105 -layout us \
  -symbols "pc+us+inet(evdev)+capslock(ctrl_modifier)+custom(ralt_super)" \
  -print >"$tmp"
xkbcomp -w 0 -I"$HOME/.config/xkb" "$tmp" "$DISPLAY"
```

Log out and back in after changing the keyboard options. If saving the
Plasma Keyboard page drops `custom:ralt_super`, re-add it to `Options=` in
`kxkbrc`.

Kanata is no longer used. Its package is kept in the repo for optional use,
but `kanata.service` is disabled and nothing starts it.

### Plasma tmux scratchpad (SUPER+F9)

`plasma` packages a KWin script that binds **SUPER+F9** to a niri-style
floating tmux scratchpad, mirroring niri's `Mod+F9` "OpenCode" binding. KWin
cannot spawn processes, so the shortcut starts `plasma-toggle-tmux@.service`,
which runs the `plasma-toggle-tmux` Perl helper (in the `scripts` package) to
do the actual toggle. After stowing, run this once:

```bash
plasma-toggle-tmux --install
```

`--install` enables the KWin script, removes the old perlbrew-pinned drop-in,
and installs a session autostart entry that reloads the script (in case KWin
came up before the script was enabled). The helper runs with
`#!/usr/bin/env perl`, so it uses the perl from the session `PATH` (the system
perl has `Net::DBus`); no perlbrew path is written anywhere. It also
pins a single **Scratchpads** button
(`tmux-scratchpad.desktop`) to every Icons-only Task Manager. All
scratchpads run kitty with the same `--class tmux-scratchpad`, so their windows
pool under that one button: Plasma shows the window count and scrolling over
it cycles through them. Right-click the button for the per-session toggle
actions (opencode, kilo, work, btop); clicking it with nothing open starts the
`opencode` scratchpad. It uses kitty's stock `Icon=kitty`, while the custom
`kitty.desktop` keeps its ember icon, so manual kitty sessions and scratchpads
are easy to tell apart. The script's `metadata.json` declares
`"X-Plasma-API": "javascript"`, so KWin loads it natively at login **and after
a compositor restart**; without that key KWin silently ignores the script and
the shortcut only works while it has been loaded by hand. **SUPER+F9** then
spawns a
centered, always-on-top Konsole running the `opencode` tmux session,
**SUPER+SHIFT+F9** does the same for `kilo`, and
**SUPER+\\** (backslash) does the same for the `work` session in Konsole, and
**SUPER+F11** for the system monitor in kitty (uses `dgop` if present, else
`htop` → `btop` → `top`); pressing
a binding again while its window is focused closes the window (the tmux session
survives). The window defaults to 90% width × 85% height of the active screen
(`--width`/`--height`), and window class matching handles both Wayland app-ids
(`org.kde.konsole`) and X11 WM_CLASS (`konsole`). Scratchpads get normal window
decorations (titlebar and resize border) even though kitty's global config sets
`hide_window_decorations yes`; pass `--no-border` to keep them frameless. Add
more scratchpads by appending to `sessions` in
`plasma/.local/share/kwin/scripts/plasma-toggle-tmux/contents/code/main.js`.

> **Do not enable** the `plasma-toggle-tmux@*.service` units. They have no
> `[Install]` section on purpose: they are one-shot toggle actions started on
> demand by the KWin shortcut. Enabling them runs a toggle at every login and
> fails, because no scratchpad window exists yet.

### S.T.A.L.K.E.R. Anomaly (`games`)

Anomaly is a standalone Windows build, so it runs through Lutris/GE-Proton.
`stalker-anomaly` automates the whole install: unpack the 7z release, create a
Win10 prefix, and register the game in Lutris with gamescope + the dGPU pinned.

```bash
stalker-anomaly status     # what it found (dest, prefix, exe, runner, Lutris id)
stalker-anomaly setup      # extract + prefix + register (idempotent)
stalker-anomaly register   # rewrite only the Lutris entry (--force to replace)
stalker-anomaly run        # launch via `lutris lutris:rungame/stalker-anomaly`
```

Notes:

- The shipped launcher (`AnomalyLauncher.exe`) is a .NET app, so the script
  bypasses it and runs `AnomalyDX11AVX.exe` directly (falling back to
  non-AVX/older renderers when the CPU/files don't support them). Renderer and
  resolution live in `~/Games/Anomaly/appdata/user.ltx`.
- `--runner` overrides the Wine build; the default is the newest `GE-Proton*`
  under `~/.local/share/lutris/runners/wine`. `--gpu` changes the
  `DXVK_FILTER_DEVICE_NAME` substring used to pick the dGPU on dual-GPU boxes.
- Wayland: the game is wrapped in gamescope (`-f`), which avoids X-Ray's
  fullscreen quirks under Xwayland. `--no-gamescope` disables that.
- If Lutris was already running during registration, restart it to see the entry.

Requires `7z` (p7zip), `sqlite3`, and `lutris`; `gamescope` is optional.
